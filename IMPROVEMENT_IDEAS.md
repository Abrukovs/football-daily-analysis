# Improvement Ideas

Документ содержит практический план дальнейшего развития проекта: автоматический деплой через GitHub Actions и улучшение прозрачности футбольного анализа.

Русское название документа: **«Идеи по улучшению»**.

## Почему выбран Markdown

Формат Markdown (`.md`) лучше всего подходит для этого материала, потому что:

- он читается прямо на GitHub;
- поддерживает заголовки, списки, таблицы и блоки кода;
- легко редактируется без специальных программ;
- хорошо хранится в Git и показывает историю изменений;
- его можно позже преобразовать в HTML или PDF.

## Часть 1. Автоматический деплой через GitHub Actions

### Что будет происходить

После каждого push в ветку `main` GitHub Actions сможет автоматически:

1. получить последнюю версию проекта;
2. подключиться к серверу по SSH;
3. скопировать файлы проекта;
4. при необходимости установить зависимости;
5. перезапустить приложение или сервис.

Схема:

```text
Изменение файла
      ↓
git commit + git push
      ↓
GitHub Actions
      ↓
SSH-подключение к серверу
      ↓
Копирование проекта
      ↓
Перезапуск приложения, если нужен
```

Для текущего проекта, который в основном содержит Markdown-отчёты, достаточно копировать файлы на сервер. Если позже появится программа или веб-приложение, workflow можно расширить установкой зависимостей и перезапуском сервиса.

### Что понадобится

- Linux-сервер;
- IP-адрес или доменное имя сервера;
- отдельный пользователь, например `deploy`;
- SSH-доступ;
- папка проекта, например `/opt/football-daily-analysis`;
- отдельный SSH-ключ для GitHub Actions.

### Создание пользователя на сервере

На сервере:

```bash
sudo adduser --disabled-password --gecos "" deploy
sudo mkdir -p /opt/football-daily-analysis
sudo chown -R deploy:deploy /opt/football-daily-analysis
```

Не рекомендуется использовать для деплоя пользователя `root`.

### Создание SSH-ключа

На административном компьютере создаётся отдельная пара ключей:

```bash
ssh-keygen -t ed25519 -C "github-actions-football-deploy"
```

Публичный ключ с расширением `.pub` добавляется на сервер в:

```text
/home/deploy/.ssh/authorized_keys
```

Приватный ключ не добавляется в репозиторий. Он сохраняется в GitHub Secrets.

Проверка подключения:

```bash
ssh -i github-actions-football-deploy deploy@SERVER_ADDRESS
```

### Секреты GitHub Actions

В GitHub откройте:

```text
Repository → Settings → Secrets and variables → Actions → New repository secret
```

Создайте следующие секреты:

| Имя | Содержание |
|---|---|
| `DEPLOY_HOST` | IP-адрес или домен сервера |
| `DEPLOY_USER` | например, `deploy` |
| `DEPLOY_PORT` | обычно `22` |
| `DEPLOY_PATH` | например, `/opt/football-daily-analysis` |
| `DEPLOY_SSH_KEY` | содержимое приватного SSH-ключа целиком |

Приватный ключ имеет вид:

```text
-----BEGIN OPENSSH PRIVATE KEY-----
...
-----END OPENSSH PRIVATE KEY-----
```

Секреты нельзя помещать в `README.md`, обычные файлы, commit-сообщения или issues.

### Пример workflow

Создайте файл `.github/workflows/deploy.yml`:

```yaml
name: Deploy football reports

on:
  push:
    branches:
      - main

permissions:
  contents: read

jobs:
  deploy:
    name: Deploy to server
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Install SSH and rsync
        run: |
          sudo apt-get update
          sudo apt-get install -y openssh-client rsync

      - name: Configure SSH
        env:
          DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
          DEPLOY_PORT: ${{ secrets.DEPLOY_PORT }}
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          mkdir -p ~/.ssh
          chmod 700 ~/.ssh
          printf '%s\n' "$DEPLOY_SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          ssh-keyscan -p "$DEPLOY_PORT" -H "$DEPLOY_HOST" >> ~/.ssh/known_hosts
          chmod 644 ~/.ssh/known_hosts

      - name: Copy project to server
        env:
          DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
          DEPLOY_USER: ${{ secrets.DEPLOY_USER }}
          DEPLOY_PORT: ${{ secrets.DEPLOY_PORT }}
          DEPLOY_PATH: ${{ secrets.DEPLOY_PATH }}
        run: |
          rsync -az --delete \
            -e "ssh -i ~/.ssh/deploy_key -p $DEPLOY_PORT" \
            --exclude ".git/" \
            --exclude ".github/" \
            --exclude ".env" \
            ./ \
            "$DEPLOY_USER@$DEPLOY_HOST:$DEPLOY_PATH/"
```

### Важное замечание о `--delete`

Параметр `--delete` удаляет на сервере файлы, которых больше нет в GitHub. Это удобно для точного зеркалирования проекта, но опасно, если в той же папке находятся пользовательские данные.

В таком случае добавьте исключения:

```yaml
--exclude "logs/"
--exclude "uploads/"
--exclude "data/"
```

Перед первым использованием лучше сделать резервную копию серверной папки.

### Если на сервере появится приложение

После копирования можно добавить шаг перезапуска:

```yaml
- name: Restart application
  env:
    DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
    DEPLOY_USER: ${{ secrets.DEPLOY_USER }}
    DEPLOY_PORT: ${{ secrets.DEPLOY_PORT }}
    DEPLOY_PATH: ${{ secrets.DEPLOY_PATH }}
  run: |
    ssh -i ~/.ssh/deploy_key -p "$DEPLOY_PORT" \
      "$DEPLOY_USER@$DEPLOY_HOST" \
      "cd '$DEPLOY_PATH' && ./deploy/restart.sh"
```

Для текущего архива отчётов перезапуск не требуется.

### Как проверять деплой

Откройте:

```text
GitHub repository → Actions
```

- зелёная галочка означает успешный деплой;
- красный крестик означает ошибку;
- подробный лог находится внутри конкретного запуска workflow.

Если сервер был недоступен, commit в GitHub всё равно сохранится. После исправления проблемы workflow можно запустить повторно через **Re-run jobs**.

### Дополнительные меры безопасности

Для production-сервера рекомендуется:

- использовать отдельного пользователя `deploy`;
- запретить вход под `root`;
- использовать отдельный SSH-ключ только для деплоя;
- ограничить права пользователя папкой проекта;
- разделить папки проекта, логов и пользовательских данных;
- хранить секреты только в GitHub Secrets или защищённом хранилище;
- фиксировать fingerprint сервера, а не безусловно доверять каждому результату `ssh-keyscan`;
- иметь резервную копию перед синхронизацией с `--delete`;
- разделять тестовый и production-сервер.

## Часть 2. Идеи для повышения прозрачности анализа

Файл `METHODOLOGY.md` описывает основную методику. Ниже перечислены полезные расширения.

### 1. Журнал решений

Для каждого рассмотренного кандидата можно фиксировать:

```text
Матч:
Рынок:
Коэффициент:
Почему рассмотрен:
Почему выбран или исключён:
Основной риск:
Итоговая оценка:
```

Так будет виден не только финальный выбор, но и причины отказа от других матчей.

### 2. История линии

Полезно указывать:

- коэффициент при первом обнаружении;
- коэффициент при финальной проверке;
- время каждой проверки;
- источник линии;
- направление движения коэффициента.

Пример:

```text
Первичная линия: 1,72 в 05:06 MSK
Финальная проверка: 1,64 в 05:31 MSK
Изменение: снижение коэффициента
Источник: OddsMath
```

Снижение коэффициента — только дополнительный сигнал, а не доказательство правильности прогноза.

### 3. Разделение фактов и интерпретаций

Каждый аргумент можно разделять на три части:

```text
Факт: команда выиграла 4 из последних 5 матчей.
Интерпретация: текущая форма поддерживает ML.
Риск: четыре победы были одержаны над соперниками из нижней части таблицы.
```

Это помогает не выдавать мнение за статистический факт.

### 4. Категории качества источников

Источники можно разделять так:

- **A** — официальный сайт UEFA, клуба или лиги;
- **B** — крупный статистический или спортивный ресурс;
- **C** — аналитический сайт или модель;
- **D** — поисковый сниппет, социальная сеть или непроверенный прогноз.

Сильный вывод не должен основываться только на источниках категорий C или D.

### 5. Ограниченная шкала уверенности

Можно указывать не только «высокая» или «средняя», но и объяснять ограничение:

```text
Уверенность: средняя.
Почему не высокая: у фаворита проблемы в обороне, а соперник хорошо играет на выезде.
```

Не следует создавать видимость математической точности там, где данных недостаточно.

### 6. Неизвестные данные

В каждом отчёте полезно указывать, что ещё не подтверждено:

```text
Неизвестно на момент проверки:
- окончательные стартовые составы;
- состояние одного игрока;
- актуальный коэффициент у конкретного букмекера;
- точная мотивация после предыдущего матча.
```

Прозрачность включает не только известные факты, но и ограничения анализа.

### 7. Post-match разбор

После матча можно добавлять отдельный блок, не изменяя исходный прогноз задним числом:

```text
## Разбор после матча

Фактический результат:
Первоначальный рынок:
Что подтвердилось:
Что не сработало:
Вывод для методики:
```

Важно отличать ошибку анализа от обычного неблагоприятного исхода. Хороший прогноз может проиграть из-за случайного события.

### 8. Проверка калибровки

Через длительный период можно сравнивать:

- прогнозируемую вероятность;
- фактическую частоту прохода;
- коэффициент;
- движение линии;
- результат по каждому рынку.

Если варианты с оценкой около 60% проходят только в 45% случаев, значит оценка слишком оптимистична или отбор недостаточно строг.

### 9. Правило остановки

Нужно явно зафиксировать:

> Анализ прекращается, когда найдено не более двух хорошо подтверждённых вариантов или когда оставшиеся кандидаты не проходят критерии качества. Дополнительный поиск не выполняется ради обязательного заполнения лимита.

Это защищает от случайного выбора после неудачного поиска.

### 10. Поздние новости

Если после публикации отчёта подтверждённая новость существенно меняет состав, мотивацию или линию, вариант нужно пометить как требующий повторной проверки. Старый коэффициент нельзя представлять как актуальный.

### 11. История изменений методики

Полезно вести журнал изменений:

```text
2026-10-14:
- добавлено правило о разделении фактов и интерпретаций;
- введено обязательное указание неизвестных данных;
- уточнено, что два варианта являются максимумом, а не обязательным количеством.
```

Так можно проследить, как система анализа развивается.

## Главный принцип

Максимум два варианта — это ограничение, а не обязательное количество. Один сильный вариант или честное отсутствие подходящего исхода лучше, чем добавление слабого прогноза ради заполнения списка.
